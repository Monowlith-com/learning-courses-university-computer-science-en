# Decision guide M1-L3–M1-L7 – From the algorithm to a reliable system

## A common framework for thinking {#S1}

An application may appear to work correctly in terms of its intended function and yet be slow, prone to errors or insecure. The reason is that the question of a **correct result** is not the same as the question of **efficient computation, reliable storage, repeatable execution or secure transmission**. The five chapters examine different points along the same path:

``` text
M1-L3: Which data structure and which algorithm?
                 ↓
M1-L4: How are modules and interfaces designed?
                 ↓
M1-L5: Which changes remain consistent as a group?
                 ↓
M1-L6: How are communication and access protected?
                 ↓
M1-L7: What happens during concurrent or repeated execution?
```

This sequence is a **thinking aid**, not a prescribed order of implementation. For example, security requirements and the data model must be considered together as early as the initial design.

## Case 1 – The growing media catalogue {#S2}

**Initial situation:** A local media catalogue grows from 500 to 50,000 entries. Users frequently search for a unique media identifier and occasionally for a date range.

**Algorithmic perspective (M1-L3):** With 50,000 entries, a linear search requires up to 50,000 equality checks in the worst case. Binary search in a sorted, directly addressable sequence requires at most 16 comparisons at this scale ($2^{15}<50\,000<2^{16}$). Under favourable assumptions, a suitable hash table provides expected constant-time access by key; it does not automatically answer date-range queries efficiently. The figures compare **modelled comparison steps**, not actual milliseconds. Building a sorted structure in the first place also requires work, as does maintaining it when changes occur.

**Software and data perspective (M1-L4/M1-L5):** A search module can change its internal implementation without rewriting the user interface. For recurring complex queries, an SQL database with suitable indexes may be simpler than maintaining custom search structures; the query plan need not use every index. Cloud clusters or microservices are unnecessary for a small single-user application.

**Security and operational perspective (M1-L6/M1-L7):** Public ports are unnecessary for purely local use. If multi-user access is introduced later, fast search indexes alone are insufficient; every query must respect the permissions for the relevant data. A shared cache must not mix user data between accounts.

**Decision:** First clarify access patterns and actual bottlenecks, then choose an appropriate structure; introduce new infrastructure last. Connections: [M1-L3](M1-L3.md), [M1-L4](M1-L4.md), [M1-L5](M1-L5.md).

## Case 2 – A job arrives twice {#S3}

**Initial situation:** Two workers receive the message “Start job 4711” at almost the same time. The job incurs a cost; executing it twice would be incorrect from a business perspective.

**Dangerous sequence:**

``` text
Worker A: no completed result found for 4711
Worker B: no completed result found for 4711
Worker A: start processing that incurs a charge
Worker B: start processing that incurs a charge
```

Neither individual check was obviously wrong, but their **combination** is insufficient. A local mutex on worker A does not help if worker B runs on another computer. The problem concerns state machines (M1-L4), database integrity (M1-L5) and concurrency (M1-L7) at the same time.

**One possible protection model:** By using a unique job key and an atomic insertion or state transition, a database can ensure that, under the relevant database assumptions, **only one worker acquires local responsibility for the job**. Computation and delivery of the result then follow a defined state model; failures may require another worker to take over. External payments need separate protection against repeated execution, supported by the payment provider. If a message is to be sent to another system after a successful database change, the intention to send it can be stored **together with the business data** as an outbox record and dispatched later; the recipient must still account for possible duplicates.

**What this does not claim:** Neither “every message is delivered exactly once” nor “every external effect is reversed by a database rollback”. The actual guarantees depend on the systems involved and the correctness of the implementation.

**When is this unnecessary?** A distributed job protocol would be excessive for a fully synchronous local process that runs only once, with no repeated execution and no external effects.

Sources and further study: [AWS – Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [M1-L4](M1-L4.md), [M1-L5](M1-L5.md), [M1-L7](M1-L7.md), [M4-L1](M4-L1.md).

## Case 3 – A secure connection and an insecure business operation {#S4}

**Initial situation:** A public web API provides a protected HTTPS entry point. The service is intended to debit an account balance and start an AI computation. The developers establish that the transmission is secured with TLS.

This is necessary, but **does not yet establish the correctness of the debit**. HTTPS protects transport **between the TLS endpoints involved**; the server must still correctly handle user permissions, account balances, repeated requests and database changes. Even with a correctly verified certificate, an application could return someone else’s account record if authorisation is missing.

In addition, certain resumed QUIC connections support **0-RTT**: under certain conditions, early application data can be replayed by attackers. Such data must not be used without appropriate checks for business operations that are not safe to repeat. The fundamental security principle is that **transport encryption, identity verification, authorisation checks and protection against repeated execution are four separate security tasks.**

Connections: [M1-L6](M1-L6.md), [M1-L4](M1-L4.md); standards: [RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html) and [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html).

## Which question belongs to which subject area? {#S5}

| Observation | First question to investigate | Relevant course area |
| --- | --- | --- |
| Searches become slow as the volume of data grows | Unsuitable access structure, index or algorithm? | M1-L3, M1-L5 |
| A change causes errors elsewhere | Unclear responsibilities and interfaces? | M1-L4 |
| Two changes leave an inconsistent state | Appropriate transaction boundaries and isolation? | M1-L5, M1-L7 |
| The same job generates multiple payments | Local atomicity confused with external idempotency? | M1-L4, M1-L5, M1-L7, M4-L1 |
| Data is protected during transmission, but other users can see it | Missing authorisation check? | M1-L4, M1-L6 |
| A failure after the commit prevents a message from being sent | Two independent systems without a reliable handover? | M1-L5, M4-L1, M7-L3 |
| A test passes, yet an edge-case error occurs | Untested assumptions or inputs? | M1-L4, M7-L2 |

## A limit of scientific claims {#S6}

A simplified comparative model shows which questions should be asked. It replaces neither measurements on the target hardware nor formal proofs of correctness or operational recovery tests. Similarly, standards such as TLS and protocol patterns such as the outbox pattern provide only **building blocks with specific prerequisites**. A fully secure and correct system as a whole does not automatically follow from them.
