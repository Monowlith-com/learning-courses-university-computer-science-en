# From an AI model to a controllable system – decision guide M5-L1–M6-L7

**Context:** Supplementary reading for modules M5 and M6. **Not a new lesson or a Master’s elective module.** All the calculations and situations below are constructed examples, not test measurements of real software or hardware. The in-depth review is documented in Review Report 17.

## 1. The ten lessons as a coherent decision-making path {#S1}

The historical perspective in [M5-L1](M5-L1.md) shows that AI is not a single method. The computational models in [M5-L2](M5-L2.md) and learning methods in [M5-L3](M5-L3.md) explain how parameters are adjusted using data. The Transformer architecture in [M6-L1](M6-L1.md), request processing in [M6-L2](M6-L2.md) and post-training in [M6-L3](M6-L3.md) lead to present-day model use. [M6-L4](M6-L4.md) turns the model into part of an application. [M6-L5](M6-L5.md) extends the inputs and outputs to include media. [M6-L6](M6-L6.md) describes the resources, and [M6-L7](M6-L7.md) the transition to physical effects.

The distinction is crucial: **model quality, application quality, organisational authorisation and physical safety each require separate evidence.** Convincing text output cannot guarantee an error-free database action, correct permission checks or safe robot movement.

## 2. Five layers of an AI application {#S2}

``` text
User request and permitted purpose
          |
          v
Application: identity, permissions, task rules
          |
          +----> permitted data access / source evidence
          |
          v
AI model: prediction, recognition, suggestion
          |
          v
Verification: evidence, schema, risks, approval
          |
          v
Execution: response or controlled action
          |
          v
Auditable result / feedback
```

**Data layer:** A media archive contains original images, metadata and optionally embeddings. A vector index is only a search aid, not a register of truth or a backup of the original files. For exact identifiers, database transactions and clear file paths, conventional methods are often simpler.

**Model layer:** A language model can formulate texts and structure suggestions. It does not automatically know which file belongs to the current user or whether an order has been paid for. Pre-training and instruction tuning are not substitutes for live data queries.

**Workflow layer:** A retrieval system may miss relevant passages or return old versions. The application needs genuine source identifiers, version information, up-to-date access control and additional authorisation for critical actions. A generated source title is not in itself evidence.

**Operations layer:** The same model can run on a local computer, a single GPU server or a distributed service. Different context lengths and numbers of concurrent users affect the KV cache and the queue in particular. More GPUs do not help with every kind of bottleneck.

**Physical effects layer:** In robotics, a model suggestion is only translated into a permitted goal-directed task. Stop functions, protective zones and safety-critical control do not belong in an uncontrolled language model dialogue.

## 3. Why a good benchmark does not automatically mean a good product {#S3}

Suppose an image classifier achieves a high accuracy rate on a prepared test set. This does not establish that it works reliably with backlighting, new cameras, poorly labelled images or a different user group. An automated LLM evaluator may also overlook an unsupported statement. It is therefore useful to assess **data coverage**, **task quality**, **error categories**, **safety conditions**, **response time** and **ongoing costs** separately.

A test for a document assistant must, for example, cover at least the cases of *the correct current source*, *no suitable source*, *conflicting versions*, *missing authorisation*, *authorisation subsequently revoked* and *a manipulated source passage*. The absence of a source must lead to an appropriately limited response, not the invention of a reference. For actions, effectiveness, approval and duplicate processing must also be tested.

## 4. Memory as a composite budget {#S4}

The parameter calculation in M6-L6 is only the first layer. A fictional model with seven billion parameters requires **14.0 GB of weight data alone** in a simplified 16-bit representation; at an idealised four bits it would require **3.5 GB**, in each case excluding additional memory requirements. Real quantisation must accommodate scaling values and runtime buffers, among other things.

A separate teaching example with 24 layers, 8 KV heads, 64 values per head, 4,096 token positions and two bytes per value gives **192 MiB of KV cache per sequence**. Eight separate sequences of equal length would therefore require **1.5 GiB**. Eight requests cannot be assessed solely on the basis of the statement ‘The model fits into 8 GB of graphics memory’. Some real architectures use GQA, sliding windows or quantised caches; their requirements may differ considerably.

The right question is not merely *How many parameters?*, but: *Which model version, numeric format, context window, degree of concurrency, cache strategy and runtime system?* Only then do load tests and a reliable economic assessment make sense.

## 5. Three architectural decisions {#S5}

### Case A – Private media catalogue

**Goal:** Find photos and videos by name, recording date and approximate content.

**Simple approach:** File index + metadata database + conventional full-text search if needed. **Extension:** Image/text embeddings for semantic search and a separate preview. **Avoid:** A large, constantly running agent system that continuously sends all files to a third-party provider without demonstrated additional benefit. Indexing should be repeatable; its results are not immutable facts about image contents.

### Case B – Document-based specialist assistant

**Goal:** Answer a question using authorised and currently valid documents.

``` text
Identity + authorisation
          |
          v
Authorised retrieval + version filter
          |
          v
Passages with genuine source identifiers
          |
          v
Model response as a DRAFT
          |
          v
Check against source + output permissions
          |
          v
Response with traceable evidence
```

**Failure case:** The user's authorisation is revoked after the index has been built. An old copy in the search index or cache must no longer be returned as an authorised result. Even a correct quotation from an unauthorised source would be a security failure. Permission checks must take place independently of the model's claims.

### Case C – A robot handles an object

**Goal:** Identify a box in a room, pick it up and take it to the permitted destination.

**Model task:** Translate verbal intent into a structured, limited task. **Planning task:** Calculate the specific position and a traversable route, and check free space and collision risks. **Safety task:** Provide independently monitored protective measures and permissible states. **Verification requirement:** Ambiguity about the box, an unknown person in the work area or an unexpected obstacle must not trigger an autonomous risky movement.

An **emergency stop** is not simply the instruction ‘Stop!’ addressed to a chatbot. Likewise, a planned ROS 2 action cancellation is not necessarily equivalent to a safety-related stop.

## 6. Provenance and labelling of AI media {#S6}

**C2PA** can make signed information about creation and editing traceable. However, the signature does not make media content true, nor does the absence of a signature guarantee manipulation. Provenance verification and content verification are different questions.

**Article 50 of the EU AI Act**, according to the Commission's current position, has applied since **2 August 2026**, with a narrowly limited grace period until **2 December 2026** for marking and detectability under paragraph 2 for systems placed on the market before then. Those who produce or publish content must consider their specific role as provider or deployer, exemptions and the applicable law. A single C2PA marker does not replace this assessment.

## 7. Five questions for choosing an architecture {#S7}

1.  **Which result can be verified?** A search result, an answer supported by sources, an approved action or a safely executed movement?
2.  **Which data are required?** Can simple rules, a conventional search or a database solve the problem without AI?
3.  **Who may read and do what?** Where are permissions technically enforced and how are changes taken into account?
4.  **Which error is costly or dangerous?** Mere textual inaccuracy, incorrect billing, a data protection breach or a physical hazard?
5.  **How is the decision verified?** Separate metrics for quality, safety, latency, costs and recovery rather than a single overall score.
