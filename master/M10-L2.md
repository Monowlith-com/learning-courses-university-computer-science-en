# M10-L2 – Data modelling and database queries in depth {#L2}

**Course area:** M10 – Bachelor: Networks and databases

**Level:** Bachelor

**Prior knowledge:** [M1-L5](M1-L5.md) · [M3-L1](M3-L1.md) · [M3-L5](M3-L5.md) · [M8-L1](M8-L1.md)

**Classification:** Understanding computer science – optional Bachelor elective topic 8 of 8.

**Note:** The aim is to reason through a real information task so that it becomes clear which tables are useful, what queries actually evaluate, why apparently identical queries return different results and what operational consequences a database structure entails.

## Data modelling: the actual question comes before the database {#S1}

**Data modelling** means translating real objects, processes and relationships into a comprehensible structure of data and rules. It begins neither with the choice of a database product nor with writing SQL. First, we need to answer: *Which things exist in the domain, how do we recognise them again, and which statements about them must remain true over time?*

Imagine a local media catalogue. It manages channels, videos and tags. In this simplified example, each video belongs to exactly one channel; a video may have several tags, and a tag may be assigned to several videos. A channel may exist before its first video has been recorded. A video may initially have no tags.

These seemingly unremarkable sentences are already important **business rules** – more precisely, domain consistency rules. They determine the subsequent tables, keys and the nature of the search queries. Here, 'business' does not imply making a profit; software engineering also uses the term for the rules of a private archive.

``` text
Real question: Which videos of a channel have the tag 'Natur' (nature)?
                   |
                   v
Domain model: Channel -- owns --> Video <-- has --> Tag
                   |
                   v
Logical model: Tables, unique keys and relationships
                   |
                   v
Physical implementation: specific DBMS, indexes, storage, backups
                   |
                   v
SQL query --> filtered, ordered result rows
```

Three levels should be distinguished:

| Level | Guiding question | Example |
| --- | --- | --- |
| **Conceptual** | What exists in the domain? | Channels, videos and tags; a channel has many videos |
| **Logical** | How is the information structurally related? | `kanal_id` as a reference from `video` to `kanal` |
| **Physical** | How is the design implemented in the chosen system? | Data types, B-tree indexes, storage layout, partitioning |

**Use:** Even for a small catalogue used over a longer period, this approach helps avoid ambiguities later. **Overengineering:** A formal diagram is usually unnecessary for five unchanging values in a configuration file. **Risk:** Oversimplifying reality leads to later data loss or contradictory special cases – for example, if a video can belong to several channels, contrary to the original assumption.

## Entities, properties, keys and cardinalities {#S2}

An **entity** is a distinct object in the domain, such as a video. Its **attributes** are properties, such as title, publication date and number of views. A **relationship** describes a verifiable connection, such as 'video belongs to channel'.

A **cardinality** describes how many objects may be linked to one another. Common examples are:

- **1:1:** A person has at most one particular profile, provided that the domain model explicitly stipulates this rule.
- **1:n:** A channel owns many videos; each video refers to one channel.
- **n:m:** Videos and tags may each be associated with several of the other kind; this usually requires a junction table.

**Optionality** must also be clarified: must a relationship exist? In our example, a video has exactly one channel but possibly zero tags. There is a crucial difference between `NULL` meaning 'no channel known' and a video without a channel that is prohibited by the domain rules.

``` text
KANAL (1) ---------------- (0..n) VIDEO
                                 |
                                 | (0..n)
                                 |
                            VIDEO_TAG
                                 |
                                 | (0..n)
                                 v
                               TAG

VIDEO_TAG connects the two sides of the n:m relationship.
```

A **primary key** uniquely identifies a table row; a **foreign key** enforces valid references. A **composite identifier** may consist of several columns: in `video_tag`, the pair `(video_id, tag_id)` makes a suitable primary key. This prevents the same tag from being assigned twice in exactly the same way to the same video.

A **natural key** derives from domain data, such as a genuinely immutable external identifier. A **surrogate key** is an ID specifically assigned for this purpose. Both have advantages and disadvantages: names can change and are often not globally unique; internal IDs must be maintained and correctly matched during import. An external video ID can be protected separately with `UNIQUE`, without automatically making it the internal primary key.

**Time is also part of the model.** 'Published on', 'last imported' and 'number of views at the time of measurement' are different statements. If a view count is recorded daily, a single column `aufrufe` is no longer sufficient to represent its history; an additional measurement table with timestamps would then be useful.

## A small relational model for reading {#S3}

The following schema is deliberately reduced in scope. SQL stands for *Structured Query Language*. The `CREATE TABLE` statements do not describe an assignment to be carried out, but rules that a database could subsequently enforce.

``` sql
CREATE TABLE kanal (
    kanal_id INTEGER PRIMARY KEY,
    name VARCHAR(120) NOT NULL UNIQUE
);

CREATE TABLE video (
    video_id INTEGER PRIMARY KEY,
    kanal_id INTEGER NOT NULL REFERENCES kanal(kanal_id)
        ON DELETE RESTRICT,
    titel VARCHAR(200) NOT NULL,
    veroeffentlicht_am DATE NOT NULL,
    aufrufe INTEGER NOT NULL DEFAULT 0 CHECK (aufrufe >= 0)
);

CREATE TABLE tag (
    tag_id INTEGER PRIMARY KEY,
    name VARCHAR(80) NOT NULL UNIQUE
);

CREATE TABLE video_tag (
    video_id INTEGER NOT NULL REFERENCES video(video_id)
        ON DELETE CASCADE,
    tag_id INTEGER NOT NULL REFERENCES tag(tag_id)
        ON DELETE RESTRICT,
    PRIMARY KEY (video_id, tag_id)
);
```

**`NOT NULL`** requires a value to be present. **`UNIQUE`** limits duplicates; when `NULL` values are permitted, product-specific rules need to be considered. **`CHECK`** tests an expression such as 'the number of views is not negative'. **`REFERENCES`** specifies the foreign key. **`ON DELETE RESTRICT`** is intended to prevent the deletion of a referenced parent entry, whereas **`ON DELETE CASCADE`** also deletes the associated junction rows. These deletion rules are domain decisions: a careless cascade can remove far more data than expected.

The syntax of this example is largely readable by both SQLite and PostgreSQL, but **not identical in every detail**. SQLite uses flexible typing, so `DATE` does not automatically guarantee the same behaviour as PostgreSQL's `DATE` data type. Automatic ID assignment also differs across systems unless an explicit mechanism is defined. In addition, SQLite requires foreign-key enforcement to be deliberately enabled or checked for each connection; its documented default is `OFF` for compatibility reasons, unless compiled otherwise. A declared foreign-key relationship is therefore no proof that it is actually enforced in every application runtime.

To trace the queries by hand, we use these **fictional initial data** (the literal values and identifiers in the SQL examples are retained):

**`kanal`**

| kanal_id | name |
| ---: | --- |
| 1 | Wissen |
| 2 | Technik |
| 3 | Leerkanal |

**`video`**

| video_id | kanal_id | titel | veroeffentlicht_am | aufrufe |
| ---: | ---: | --- | --- | ---: |
| 101 | 1 | Bäume | 2026-01-10 | 120 |
| 102 | 1 | Flüsse | 2026-02-01 | 80 |
| 201 | 2 | Netze | 2026-02-03 | 200 |

**`tag` and `video_tag`**

| tag_id | Name | Associated videos |
| ---: | --- | --- |
| 7 | Natur | 101, 102 |
| 8 | Technik | 201 |

The third channel row, which has no video, is not an error; it will later reveal a difference between an **INNER JOIN** and a **LEFT JOIN**.

## Why tables are separated: functional dependencies and normalisation {#S4}

A **functional dependency** states that when a certain key value is fixed, the value of another attribute is thereby determined. In the simplified model, for example, `kanal_id -> kanal.name` holds. The channel name therefore logically belongs to the channel, not to each video.

An unfavourable single table might look like this:

``` text
video_id | videotitel | kanal_id | kanalname | tag
101      | Bäume      | 1        | Wissen    | Natur
102      | Flüsse     | 1        | Wissen    | Natur
201      | Netze      | 2        | Technik   | Technik
```

If channel 1 receives a new name, the same value must be changed in several places. If a row is forgotten, an **update anomaly** arises. Deleting the only video of a channel might accidentally remove the information about the channel itself (**deletion anomaly**). It may be impossible to record a new channel without a video (**insertion anomaly**).

**Normalisation** is a systematic way of organising such repetitions and dependencies. For reading purposes, it is sufficient to develop an accurate basic intuition for three frequently discussed normal forms:

| Normal form | In simplified terms | What question do we ask? |
| --- | --- | --- |
| **1NF** (first normal form) | Values are atomic within the chosen relational model; no repeating column groups | Are 'tag1, tag2, tag3' placed next to each other as artificially fixed columns? |
| **2NF** (second normal form) | In 1NF; non-key attributes do not depend on just a proper subset of a composite candidate key | Does a tag name really belong to the assignment `(video_id, tag_id)` or to the table `tag`? |
| **3NF** (third normal form) | In 2NF; impermissible transitive non-key dependencies are avoided | Does `video_id` determine `kanal_id`, which in turn determines the channel name? |

The formal definitions are more precise than these rules of thumb and require clarity about **candidate keys** and the relevant functional dependencies, among other things. An artificially unique ID key alone does not eliminate domain redundancy.

By separating `kanal`, `video`, `tag` and `video_tag`, the respective name is maintained at the appropriate place in the domain model. **Denormalisation** can nevertheless be useful: a very frequently queried counter or a precomputed summary is sometimes stored in addition. Updating, staleness and consistency then become new problems. A fast report is not automatically a better data model.

**When is normalisation excessive?** In a small, one-off exported analysis, repeating column values may be readable and practical. In a database that is continually edited, the rules are more important. Image files, videos and free text do not necessarily have to be broken down into relational tables in every detail either.

## SQL queries are declarative: the result is described {#S5}

An SQL query primarily describes **which rows and columns** are needed. The database optimiser may choose the execution path itself. In simplified terms, the following conceptual stages can be distinguished:

``` text
FROM / JOIN  ->  WHERE  ->  GROUP BY  ->  HAVING
     -> SELECT expressions  ->  ORDER BY  ->  LIMIT
```

This is a **didactic logical model**, not a binding physical execution order. Window functions and database-specific details in particular need closer consideration. The optimiser can apply filters early, arrange joins differently or use indexes as long as the semantics are preserved.

``` sql
SELECT titel, aufrufe
FROM video
WHERE kanal_id = 1 AND aufrufe >= 100
ORDER BY aufrufe DESC, video_id ASC;
```

Of our three video rows, the query returns only 'Bäume' with 120 views. `WHERE` excludes rows that do not meet the criterion. `ORDER BY` specifies the order explicitly; without this clause, a stable order is **not guaranteed**, even if individual tests always produce the same picture.

**SQL generally uses multisets rather than pure mathematical sets.** A result table may contain several identical-looking rows. `DISTINCT` removes duplicate results with respect to the selected columns, but not the underlying records. This is especially important for joins and aggregates.

**`LIMIT`** restricts the output but is not a substitute for a sort order defined by the domain. If an interface is intended to display 'the 20 newest videos', it should use a unique secondary sort key in addition to the timestamp; simultaneous publications would otherwise not have a unique order. The exact syntax for limiting results varies between database products.

## JOIN: reading relationships without inadvertently multiplying data {#S6}

A **JOIN** combines rows from several tables according to a condition. An **INNER JOIN** returns only combinations with a match on both sides:

``` sql
SELECT k.name AS kanalname, v.titel
FROM kanal AS k
JOIN video AS v ON v.kanal_id = k.kanal_id
ORDER BY k.kanal_id, v.video_id;
```

The result contains three video rows, but **not** `Leerkanal`: it has no matching entry on the video side.

A **LEFT JOIN**, by contrast, includes all rows of the left table even if nothing matches on the right. The missing right-hand values appear as `NULL`:

``` sql
SELECT k.name, v.titel
FROM kanal AS k
LEFT JOIN video AS v ON v.kanal_id = k.kanal_id
ORDER BY k.kanal_id, v.video_id;
```

Here `Leerkanal` also appears, with `NULL` as the title. 'No matching video found' does not therefore become 'a video with an empty title'. This, too, is a domain distinction.

**A classic trap:**

``` sql
SELECT k.name, COUNT(*) AS anzahl
FROM kanal AS k
LEFT JOIN video AS v ON v.kanal_id = k.kanal_id
GROUP BY k.kanal_id, k.name;
```

For `Leerkanal`, this query counts **1**, because the result row created by the LEFT JOIN is counted as well. For 'number of existing videos', the correct expression is `COUNT(v.video_id)`: here the aggregate counts only rows with a non-null video ID and returns 0.

A further trap is possible with an n:m join. If a video has several tags, the join returns several rows **for the same video**. Anyone who then adds up all `aufrufe` values may count the views repeatedly. The solution is not automatically to apply `DISTINCT` blindly: first, the intended **grain** of the result must be defined in domain terms, such as 'one row per video', 'one row per tag assignment' or 'one row per channel'. If needed, the data is first aggregated at this correct level and then joined further.

## Filtering, grouping, NULL and three-valued logic {#S7}

The most important aggregate functions are **`COUNT`** (count), **`SUM`** (sum), **`AVG`** (arithmetic mean), **`MIN`** and **`MAX`**. An example:

``` sql
SELECT k.name,
       COUNT(v.video_id) AS videozahl,
       COALESCE(SUM(v.aufrufe), 0) AS gesamte_aufrufe
FROM kanal AS k
LEFT JOIN video AS v ON v.kanal_id = k.kanal_id
GROUP BY k.kanal_id, k.name
ORDER BY k.kanal_id;
```

| Channel | videozahl | gesamte_aufrufe |
| --- | ---: | ---: |
| Wissen | 2 | 200 |
| Technik | 1 | 200 |
| Leerkanal | 0 | 0 |

For `Leerkanal`, `SUM(v.aufrufe)` without matches is **`NULL`**. With `COALESCE(..., 0)`, this becomes 0 for the report. The decision is plausible in domain terms, but is not correct for every metric: an unknown measurement is not necessarily the same as zero.

**`NULL`** in SQL denotes the absence of a value, not the number 0 or the empty string. A normal equality test such as `spalte = NULL` does not yield the usual true/false result. SQL has three possible outcomes for conditions: **true, false and unknown**; `IS NULL` or `IS NOT NULL` is needed here. Comparisons such as `NULL = NULL` are not simply 'true' either.

The difference between `WHERE` and `HAVING` is crucial:

- **`WHERE`** filters input rows before grouping.
- **`HAVING`** filters groups according to their aggregated values.

``` sql
SELECT kanal_id, COUNT(*) AS zahl
FROM video
WHERE aufrufe >= 100
GROUP BY kanal_id
HAVING COUNT(*) >= 1;
```

This query counts only videos with at least 100 views. This is **not** the same question as 'Which channels have at least 100 views in total?'. For that, one would calculate `SUM(aufrufe)` per channel and test it in `HAVING`. A small difference in wording can mean a completely different result in domain terms.

## Subqueries, EXISTS and common table expressions {#S8}

A **subquery** is an SQL query within another. With **`EXISTS`**, we ask whether at least one matching record exists. This is particularly useful when the number of relationships does not matter, only their existence.

``` sql
SELECT v.video_id, v.titel
FROM video AS v
WHERE EXISTS (
    SELECT 1
    FROM video_tag AS vt
    JOIN tag AS t ON t.tag_id = vt.tag_id
    WHERE vt.video_id = v.video_id AND t.name = 'Natur'
)
ORDER BY v.video_id;
```

This returns videos 101 and 102, each exactly once. `EXISTS` asks whether there is a match; it does not multiply video rows like an ordinary join when several matching assignments exist.

A **common table expression (CTE)** is a named subquery incorporated into a larger query with `WITH`. It is a means of structuring a query, not necessarily a permanently stored table.

``` sql
WITH kanal_aufrufe AS (
    SELECT kanal_id, SUM(aufrufe) AS summe
    FROM video
    GROUP BY kanal_id
)
SELECT k.name, a.summe
FROM kanal AS k
JOIN kanal_aufrufe AS a ON a.kanal_id = k.kanal_id
ORDER BY a.summe DESC, k.kanal_id;
```

Here 'Wissen' and 'Technik' appear with 200 views each. `Leerkanal` is absent because of the inner join; this could be changed by a LEFT JOIN and a domain-appropriate way of handling null values.

**Important:** A CTE does not automatically make a query faster. Depending on the database system, version and structure, it may be integrated into a plan or processed separately. The form is primarily an aid to comprehensibility and to establishing a clearly named intermediate level.

## Window functions: comparing without collapsing rows {#S9}

Grouping with `GROUP BY`, for example, condenses two videos of a channel into **one channel row**. A **window function**, by contrast, can add a comparison **for each individual video row** without first collapsing the rows.

``` sql
SELECT kanal_id, video_id, titel, aufrufe,
       ROW_NUMBER() OVER (
           PARTITION BY kanal_id
           ORDER BY aufrufe DESC, video_id
       ) AS rang_im_kanal
FROM video
ORDER BY kanal_id, rang_im_kanal;
```

`PARTITION BY` separates the calculation by channel; `ORDER BY` inside the window specifies the ranking. For the knowledge channel (Wissen), 'Bäume' receives rank 1 and 'Flüsse' rank 2. 'Netze' has rank 1 in its channel. `ROW_NUMBER` counts strictly consecutively; `RANK` may assign shared ranks to equal values and skip subsequent numbers.

For running sums, the **window frame** is also important. Unless a frame is specified explicitly, product- and clause-dependent defaults apply. For example, in **PostgreSQL**, with `SUM(aufrufe) OVER (ORDER BY veroeffentlicht_am)`, the default frame also includes *peer rows* with identical publication dates; a running sum may therefore increase abruptly when dates tie. If a running sum proceeding row by row is intended, one can use an explicit frame such as `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` and a unique sort order by date **and** `video_id`. Without `ORDER BY`, on the other hand, the window calculation typically covers the whole partition. The behaviour must be distinguished according to the selected window function and the particular database system. Window functions are evaluated later than `WHERE` in logical SQL processing; an enclosing subquery or CTE is therefore typically used to filter a calculated rank.

**When useful?** Rankings, comparisons with group averages, time series and analyses containing individual entries and their group context. **When unnecessary?** A simple list of five titles does not require a complex window construction.

## Query plans and indexes: why correct SQL can still be slow {#S10}

An **index** is an additional search structure, often a variant of a balanced B-tree. It makes certain search and sorting paths more efficient, but requires storage of its own and must be updated when changes occur. The **query optimiser** (*query planner*) estimates whether an index, a table scan or a combination of several methods is suitable for the query.

``` text
SQL: Videos from channel 1, newest first
               |
               v
           Query planner
             /      \
            v        v
     Table scan    Index search on (kanal_id, date)
            \        /
             v      v
               Result
```

A common combined access pattern is:

``` sql
SELECT video_id, titel
FROM video
WHERE kanal_id = 1
ORDER BY veroeffentlicht_am DESC, video_id DESC;
```

One possible index for this is:

``` sql
CREATE INDEX ix_video_kanal_datum_id
ON video (kanal_id, veroeffentlicht_am DESC, video_id DESC);
```

The leftmost column `kanal_id` helps select a specific channel; the subsequent index columns fit the desired sort order. **Order in composite indexes matters**: an index on `(kanal_id, veroeffentlicht_am)` is not equally useful for every query that filters purely by date. The exact behaviour depends on the system, the distribution and the query plan.

To illustrate: a table of 1,000,000 videos has 1,000 channels with 1,000 videos per channel, *uniformly distributed in the model*. A filter on one channel reduces the candidates on average from 1,000,000 to 1,000 – that is, to one thousandth. This does **not** mean that an index is exactly a thousand times faster in practice: an index lookup itself takes time; data may be cached; indexes are not advantageous for every sort order or for many simultaneous changes.

**Selectivity** describes, in simplified terms, how strongly a predicate restricts the data set. A common status field such as `sichtbar = 1` might return almost all rows and does not on its own justify an index. **Statistics** on data distributions help the planner estimate the row count. Outdated statistics can lead to poor decisions.

With **`EXPLAIN`**, PostgreSQL can display the planned access method; **`EXPLAIN ANALYZE`** actually executes the query and measures real parts of its processing. This is not harmless for statements that write data – those statements are actually executed too. PostgreSQL documentation presents the controlled teaching pattern `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`: the transaction reverses the database change, but is no substitute for carefully checking other possible side effects. A theoretical planner cost value is not directly a time in milliseconds.

**Index maintenance is a trade-off:** reads may become faster, while writes require additional index updates. More indexes consume storage and may burden backups or migrations. For small tables, the database may deliberately choose a full scan; this is not automatically an error.

## Transactions: making correct changes is a task of its own {#S11}

A **transaction** combines logically related changes into one unit. `BEGIN`, `COMMIT` and `ROLLBACK` denote the beginning, confirmed completion and reversal of uncommitted changes. The **ACID** properties are familiar from [M1-L5](M1-L5.md): atomicity, consistency, isolation and durability.

Imagine two processes wanting to change the view count of a video at the same time. Both read the old value 100 and calculate 101. If both simply write back '101', one increment is lost (**lost update**). An atomic change directly to the current database value can prevent this specific error:

``` sql
UPDATE video
SET aufrufe = aufrufe + 1
WHERE video_id = 101;
```

For more complex rules, an **optimistic concurrency check** using a version column may help. A change is only permitted if the previously read version still applies. If no row is changed, the application must deliberately handle the conflict instead of ignoring it. **Locks** and higher **isolation levels** are further options, but they often increase waiting times, conflicts or the need to retry.

Example: two users reserve the same last place. The database must ensure that both confirmations cannot simultaneously appear to be valid. Simply 'checking first whether it is still free' outside a controlled transaction is insufficient under concurrency. The appropriate rule may be a unique key, an atomic conditional write or a transaction with a suitably chosen isolation level.

**Isolation levels** are not a universal set of switches with identical behaviour in all systems. PostgreSQL's `READ COMMITTED`, `REPEATABLE READ` and `SERIALIZABLE` have documented properties; under serialisable processing, transactions can be aborted and must be retried at application level. SQLite coordinates concurrent access differently, including through journal or write-ahead logging modes and limited concurrent writing capabilities. Migration from SQLite to PostgreSQL is therefore more than copying tables.

## Secure queries, user separation and data protection {#S12}

An SQL statement is not automatically secure simply because it works correctly in domain terms. **SQL injection** occurs when untrusted input unintentionally becomes SQL syntax. **Parameterised queries** are considered the most important defence: the SQL structure remains fixed, and values are bound separately through the database interface. Placeholder syntax and programming interfaces vary by driver.

``` text
Secure principle:
Fixed SQL:  SELECT video_id FROM video WHERE kanal_id = ?
Value:      1   (bound separately through the database interface)

Insecure principle:
Concatenating characters supplied by the user
with an SQL string in an uncontrolled way.
```

Placeholders are intended for **values**, not automatically for arbitrary table names, column names or `ASC`/`DESC`. For dynamic sorting options, use a small, verified set built into the application. Even correct parameter binding does not replace **authorisation**: a user could still supply the ID of someone else's record. The server must therefore enforce access rules.

In a service with several customers, one often speaks of **tenants**. A simple shared table with `mandant_id` is technically possible, but error-prone if the tenant filter is forgotten in even a single query. Alternatives include separate databases or database schemas; all variants have costs, operational consequences and security limitations. In PostgreSQL, under suitable conditions, **row-level security (RLS)** can provide additional database rules. Simply activating it does not replace checking the entire permissions and role model.

**Personal data** should be considered not only when it is collected but also during modelling: what information is necessary, how long is it stored, who may see it and how are correction and deletion carried out? Indexes, logs, export files and backups may also contain such data. Deletion routines must realistically account for retention obligations, backup cycles and technical recovery; this chapter is not legal advice.

## Schema changes: a database is not finished after its first design {#S13}

A **schema** describes tables, columns, rules and other database objects. A **migration** changes this schema or transforms the data already stored. Such changes require version management, testability and a recovery path in case of error.

Suppose `video.titel` is to be supplemented in future with an editable short name. Direct renaming can render an older program version unusable. For long-running online services, a staged approach is often useful:

``` text
1. Add the new column; continue supporting the old one
                     |
                     v
2. The application can initially read/write both forms
                     |
                     v
3. Update existing records in a controlled manner
                     |
                     v
4. Switch the new version exclusively to the new form
                     |
                     v
5. Remove the old column only after checks and rollback planning
```

This is called **expand-and-contract**. It is not a mandatory method for every application: for a purely offline tool, a planned, tested one-off transition may be easier. For a publicly used service, however, such intermediate states avoid some compatibility and downtime problems.

A **backup** before a schema change does not automatically protect against every error. One must also test whether it can be restored, whether the application is compatible with the restored data structure and which changes are lost between backup and failure. Large tables can be placed under noticeable strain when columns are altered or indexes are created; some operations block writes or create additional storage requirements. The specific properties depend on the database system and SQL statement.

## Three illustrative architecture examples {#S14}

### Example A – Private local media catalogue

A local catalogue organises video and image files with titles, tags and search criteria. In small, single-user operation, SQLite may be a simple choice: an embedded database, SQL queries, transactions and no separate database server administration.

``` text
Desktop interface
        |
        v
Media catalogue logic
        |
        v
SQLite database ----> Indexes for channel / tag / date
        |
        v
File paths to locally stored media
```

**Advantages:** straightforward operation, easy portability, no network service required. **Limitations:** a local file path does not automatically remain valid permanently; removed or renamed files create orphaned references. The database and media files require a coordinated backup strategy. With several concurrent writers, the demands on coordination and storage media increase. A cloud cluster would be unnecessary for the single-user catalogue described here.

### Example B – Small public web service

A service offers several signed-in users a search function over their own collections. A relational server DBMS such as PostgreSQL may be suitable when several clients write concurrently, access permissions have to be separated and reliable network operation is required.

``` text
Browser
   |
   v
Web API with authentication and authorisation
   |
   v
Application logic (parameterised SQL queries)
   |
   v
PostgreSQL: tables, constraints, indexes, transactions
   |
   +--> Backups / restore rehearsals
   +--> Monitoring / migrations
```

**Advantages:** central data storage and an architecture designed for concurrent users. **Costs:** server operation, security updates, access protection, backups, incident handling and possibly usage-dependent hosting fees. Making databases directly accessible on the public internet would not be a necessary feature of a web service and increases the attack surface.

### Example C – Sensor readings and time series

A device sends temperature readings regularly. A useful logical record includes at least `sensor_id`, timestamp, measured value and unit, or a clearly documented system of units.

``` text
Sensor -> Ingestion service -> validated timestamps / values
                              |
                              v
                    Measurement table by sensor and time
                              |
                              v
                    Time-window aggregates / charts
```

**Modelling questions:** can a measurement arrive late? Are repeated transmissions allowed? What does a missing measurement mean? May the sensor be recalibrated retrospectively? What time range is retained? An index on `(sensor_id, zeitpunkt)` can support repeated time-range queries; with very large data volumes, partitioning, aggregation and retention policies also become relevant. These measures raise new maintenance questions and are not essential for a few hundred readings.

## Two small, verifiable calculations {#S15}

### Example 1 – Duplicate values caused by the wrong join grain

Suppose video 101 has 120 views and receives two tags. A join of `video` with `video_tag` then creates two result rows for this video. A blind `SUM(video.aufrufe)` over this joined list returns **240** instead of **120**. This is not a calculation error by the database system; the query supplied the same video's view count twice for summation. The remedy is a domain-correct result basis per video or an appropriate aggregation beforehand.

### Example 2 – The difference between `COUNT(*)` and `COUNT(spalte)`

`Leerkanal` has no video. Its `LEFT JOIN` still produces exactly one result row in which all video columns are `NULL`. `COUNT(*)` counts rows and therefore gives **1**; `COUNT(v.video_id)` counts only present IDs and gives **0**. The right choice derives from the question, not from the superficial similarity of the two expressions.

## Decision guide {#S16}

| Question / initial situation | Often useful decision | Error to avoid |
| --- | --- | --- |
| Small local data store | Text file or SQLite, depending on requirements | Forcing a separate database server without need |
| Many related, changing data | Relationships, keys and rules in the data model | Maintaining the same names uncontrolled in many rows |
| Several tags per video | Separate assignment table | `tag1`, `tag2`, `tag3` with a fixed limit |
| Sums by category | First determine the correct grain, then group | Overlooking double counting due to joins |
| Search becomes slow | Inspect real queries and `EXPLAIN`, index selectively | Indexing every data type and every column as a precaution |
| Several users make changes simultaneously | Transactions, constraints and a conflict strategy | Read–modify–write without concurrency checks |
| Public application API | Parameter binding, authorisation, minimal database privileges | Constructing SQL from inputs; treating an ID alone as permission |
| Data model changes | Planned migration, tests, backup and rollback path | Deleting columns without considering old software versions |
| Historical measurements | Time-based data structure and retention rules | Storing only the most recent value and expecting a time series |

## Summary and connection to the rest of the course {#S17}

A good data model translates domain rules into verifiable structures. **Keys and relationships** enforce identity and association; **normalisation** prevents many data inconsistencies; **SQL** describes the desired data sets; **joins and aggregates** require an understanding of result grain; **indexes** serve specific search patterns and cost storage and write work; **transactions and permissions** protect correctness and data access. None of these techniques automatically makes the system secure, fast or easy to maintain.
