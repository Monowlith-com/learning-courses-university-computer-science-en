## Why a network is more than a cable {#S1}

A computer can process data on its own. Once several computers communicate, additional tasks arise: they must find the recipient, forward messages along the way, detect failures and decide whom to trust. A local file can be read directly. A file on another computer, by contrast, requires at least a connection, an agreed language and an access decision.

A **network** is not merely the physical cable or wireless network. It includes devices, rules, addresses, protocols, name resolution, connections to other networks and security boundaries. Two programs can communicate on the same computer using network mechanisms; conversely, an application with many servers can internally appear to be a single service.

``` text
Laptop on home network
   | Wi-Fi / Ethernet
   v
Router / internet access
   | Forwarding through several networks
   v
Public web server
   | Verified application interface
   v
Internal database (not publicly accessible)
```

**Guiding question:** Which participant may send which message to which destination – and what happens if a device, credential or network segment is compromised? Network security therefore begins with designing communication relationships and does not end with switching on a firewall.

## Layers and protocols: How data finds its way {#S2}

A **protocol** is a collection of agreed rules: who sends what information and when, what a response means and how errors are handled. The internet uses a family of protocols built upon one another. A simplified four-layer model helps to put them into context:

| Perspective | Typical technology | Question |
| --- | --- | --- |
| Application | HTTP, DNS, email protocols | What information should be exchanged? |
| Transport | TCP, UDP, QUIC | Which program endpoint? How reliable or fast? |
| Internet | IPv4, IPv6, IP routing | To which logical network address? Through which networks? |
| Network access | Ethernet, Wi-Fi | How is a data frame transmitted on the directly reachable network? |

**HTTP** (*Hypertext Transfer Protocol*) governs web requests and responses, among other things. **DNS** (*Domain Name System*) associates names such as `beispiel.invalid` with the information needed to establish a connection. **IP** (*Internet Protocol*) forwards packets between networks. **TCP** (*Transmission Control Protocol*) provides an ordered, reliable byte stream. **UDP** (*User Datagram Protocol*) transports individual datagrams without the same built-in delivery and ordering guarantees. **QUIC** combines a transport-like approach over UDP with encryption and multiple-stream capabilities; HTTP/3 uses QUIC.

**Encapsulation** means that a layer embeds the data of the higher layer into its own structure. This is comparable to a letter transported in an envelope whose address differs from an internal order number.

``` text
Application data:  "Retrieve the home page"
Transport:         Associated connection / port
Internet:          Source and destination IP addresses
Network access:    Frame to the next reachable device

Intermediate routers replace the frame for the next network.
The HTTP message remains logically the same.
```

### Switch, router and access point

A **switch** connects participants within a local network or so-called Layer 2 segment and frequently uses **MAC addresses** (*Media Access Control*, local interface addresses) for this purpose. A **router** connects different IP networks and chooses a next forwarding step. A Wi-Fi **access point** provides wireless access to a network; home routers often combine these functions in one device.

A **MAC address** is not the global internet address and is not reliable proof of a person's identity. Similarly, an **IP address** is initially a technical address, not evidence of an authorised person. With **NAT** (*Network Address Translation*), address information is translated when passing between networks. NAT can indirectly restrict certain connections but is **not a substitute for an intentionally configured security rule**.

### DNS and the question of what a name proves

An address such as `https://lernbeispiel.example` is readable by humans. Before contacting a service, one or more name resolutions normally occur. **DNS responses are not equivalent to a security assurance:** domain resolution specifies where a request should technically go. Whether the connection to the expected service is authentic and confidential must be verified separately. DNSSEC can support the authenticity of DNS data; it does not encrypt the query itself. Encrypted DNS transport methods, in turn, do not automatically resolve the question of whether a website is trustworthy.

**Typical misconception:** “I entered the correct internet address, so all the following data is secure.” Different verification steps exist between the name, address, certificate, server configuration, application permissions and user login.

## IP addresses, networks and the significance of a subnet boundary {#S3}

**IPv4** uses 32-bit addresses, often written as four decimal numbers (`192.0.2.1`). **IPv6** uses 128-bit addresses and a different notation (`2001:db8::1`). The example ranges here are intended for documentation and are not real reachable endpoints. Both protocols provide addressing and forwarding, but payload encryption does not arise automatically from using IPv6.

In **CIDR notation** (*Classless Inter-Domain Routing*), `/27` means that the first 27 of 32 bits of an IPv4 address belong to the network prefix. The remaining five bits allow $2^5 = 32$ possible addresses. In a classical IPv4 subnet, one network address and one broadcast address are usually reserved, leaving **30 conventional host addresses**. This is a teaching model; special network forms and provider allocations may differ.

| Example | Prefix bits | Address bits for hosts | Calculated IPv4 addresses |
| --- | ---: | ---: | ---: |
| `192.0.2.0/24` | 24 | 8 | 256 |
| `192.0.2.0/27` | 27 | 5 | 32 |
| `192.0.2.0/30` | 30 | 2 | 4 |

Important: **A subnet is not yet a complete security boundary.** Effective network separation requires appropriate routing and filtering rules, often supplemented by permission checks on endpoints and in applications. A misconfigured router can immediately reconnect “separate” networks.

### Three kinds of separation

- **Logical separation:** for example, different virtual local area networks (**VLANs**, *Virtual Local Area Networks*) on shared infrastructure.
- **Communication control:** rules governing which connections between segments are permitted, for example through firewalls or access control lists.
- **Physical separation:** genuinely separate cabling or devices when required by the risk model; more demanding, but not automatically free of errors.

The appropriate measure depends on protection requirements, threat model, operational feasibility and maintenance effort. Germany's BSI explicitly treats network architecture, segmentation and permitted communication relationships as planning topics in its IT baseline protection guidance (*IT-Grundschutz*).

## Ports, connections and firewalls: What is actually filtered? {#S4}

A network program is accessible via an address and usually an additional **port**. A port is a number through which the transport mechanism identifies an application endpoint. Web servers typically use `443` for HTTPS; this is a **convention**, not a guarantee that a secure web service actually operates behind that port. Two programs can reach one another on different ports of the same computer if the operating system and rules permit it.

A **firewall** examines characteristics of communication and decides according to rules whether traffic may pass. A *stateful* firewall typically tracks whether a packet belongs to an existing permitted connection. It is not equivalent to a virus scanner, user management system or comprehensive application security assessment.

**Example of a comprehensible rule policy:**

``` text
Internet
   |
   | Permitted: HTTPS to public web service
   v
[Public web service]
   |
   | Permitted: defined database access
   v
[Internal database]

Internet --------X------> [Internal database]
                     Not directly permitted
```

The **principle of least privilege** can also be applied to networks: allow only the communication paths actually required for the purpose. **Default deny** describes the basic stance of “deny initially, define exceptions explicitly”. Exceptions must be documented, reviewed regularly and removed when no longer needed.

A rule as broad as “internal computers may do everything” can endanger an entire environment if a single computer is compromised. Conversely, an overly complicated set of rules can encourage maintenance errors: security requires not the greatest possible number of rules, but verifiable, correct rules.

## Security objectives and threat model {#S5}

Three classical **security objectives** of information security are:

1.  **Confidentiality:** Unauthorised people should not be able to read data.
2.  **Integrity:** Data and functions should not be changed unnoticed or without authorisation.
3.  **Availability:** Authorised people should be able to use required services reliably.

Other objectives include **authenticity** (does a message actually originate from the expected sender?) and **traceability** (can security-relevant operations be adequately reconstructed?). Security objectives may conflict. More monitoring might detect an attack earlier, but at the same time collect unnecessary personal data. A highly isolated service may be more difficult to administer.

### The threat model in five questions

Before choosing products and protection measures, one should ask:

- **What should be protected?** For example, private media, customer data, access keys or website availability.
- **Who or what can cause harm?** Accidental misuse, defective hardware, malware, compromised accounts, abusive use or an unreliable service provider.
- **Which boundaries are crossed?** Browser to server, server to database, office PC to IoT device, own server to cloud service.
- **What damage is realistic?** Data loss, disclosure, service interruption, incorrect invoices, uncontrolled usage costs.
- **How would one notice a disruption and respond?** Logs, alerts, account suspension, recovery and communication.

A **risk** does not depend solely on a theoretical attack possibility. It takes account of the plausibility of an incident and its possible scale. Numerical models can support prioritisation but are uncertain for rare security events.

**Deliberately fictional example:** A service might incur approximately 2,000 euros in additional processing costs over 100 hours of downtime. This amounts to `20 euros per hour` as a model calculation, not an actual price or a reliable estimate of loss. Even without an attacker, a faulty backup can cause comparable damage. The threat model should therefore include **accidents and failures**.

## Encryption: What HTTPS does and does not achieve {#S6}

**HTTPS** combines HTTP with a protected transport channel, today typically using **TLS** (*Transport Layer Security*). TLS is intended to protect confidentiality and integrity during transmission and appropriately authenticate the other endpoint. A browser typically checks a certificate for the expected domain name and a trusted certificate chain. **TLS does not protect against a malicious application on the correctly authenticated server**, against abuse by authorised logged-in users, or against all metadata observation.

Since July 2026, **RFC 9846** has described TLS 1.3 and superseded the earlier TLS 1.3 specification RFC 8446. This does not mean that the protocol suddenly acquired the version number “TLS 1.4”: it remains **TLS 1.3**, but the relevant RFC document has been revised. For configuration recommendations, actual browser, server and library support is also relevant.

``` text
Browser                          HTTPS server
   |                                  |
   | Connection setup, negotiation    |
   |--------------------------------->|
   |<---------------------------------|
   | Certificate / peer verification  |
   |                                  |
   | < Protected data exchange >      |
   |==================================|
```

**Transport security** exists only between the respective TLS endpoints. If a reverse proxy terminates the TLS connection and subsequently forwards traffic internally without encryption, only the first part of the route is encrypted. A second TLS connection can be useful, but it does not replace access control. **End-to-end encryption** is a separate concept: only the intended endpoints have access to the decrypted content; ordinary HTTPS connections to a website do not automatically constitute such an architecture.

### Do not confuse hashes, signatures and passwords

- A **cryptographic hash function** computes a compact verification value from data. It is not encryption: it should not be straightforward to reconstruct the original text from the hash.
- A **digital signature** helps to verify origin and integrity when the associated keys are managed correctly.
- **Password hashes** require special slow, salted methods for human-chosen passwords; a fast general-purpose checksum hash alone is unsuitable.
- **Encryption** protects content only if keys are protected, access permissions are correct and plaintext copies are handled appropriately.

The most common error is to regard cryptography as a universal solution. An encrypted storage device is of little help if the application exposes all records to every user after login.

## Login, permissions and sessions: Three different questions {#S7}

**Authentication** answers “Who is logging in?”, whereas **authorisation** answers “What may this authenticated actor do?”. A successful login does not automatically mean that every record may be read. A **session** associates multiple requests with an already established login state. During its validity period, a session token can have a similar effect to the original authentication credential and must be protected accordingly.

**Multi-Factor Authentication (MFA)** uses evidence from different factor types, such as knowledge, possession and biometric characteristics. Additional factors mitigate many risks, but not all methods are equally robust against phishing. **Passkeys**, based on FIDO2/WebAuthn, can enable phishing-resistant authentication bound to the correct service. Device loss, account recovery and incorrect permission checks remain important issues even with this approach.

| Example | Question | Appropriate control point |
| --- | --- | --- |
| Successful login | Is it the correct person or key? | Authentication |
| Retrieve media catalogue `4711` | Does the entry belong to this user? | Server-side authorisation |
| Cookies after login | Was an unpredictable, correctly protected token issued? | Session management |
| Access expired | May old requests still be accepted? | Expiry and revocation |

**Important architectural principle:** A hidden button in a user interface is not a permissions model. The application must check access on the server or a comparably trusted component **for every relevant operation**. Even if an attacker guesses an address or manually constructs a request, other users' data must not be disclosed.

## Typical application weaknesses: The OWASP perspective {#S8}

The **Open Worldwide Application Security Project (OWASP)** community publishes security material for web applications. The **OWASP Top 10:2025** is an awareness list of major risk categories, **not a comprehensive security catalogue or a guarantee of particular frequencies in one's own project**.

| Area (OWASP 2025) | What can go wrong? | Defence principle |
| --- | --- | --- |
| A01 Broken Access Control | Users access other users' data or functions. | Server-side checks of each object and operation |
| A02 Security Misconfiguration | Debug mode, unnecessary services, overly permissive rules. | Secure initial configuration, traceable changes |
| A03 Software Supply Chain Failures | Dependencies, builds or distribution paths are compromised. | Verify provenance, updates, permissions and approvals |
| A04 Cryptographic Failures | Data is protected incorrectly or incompletely. | Established standards, correct key and certificate management |
| A05 Injection | External input is inadvertently treated as a command. | Parameterised queries and appropriate interfaces |
| A06 Insecure Design | Protection rules are already missing from the basic model. | Threat modelling, data flow and permission design |
| A07 Authentication Failures | Login, account recovery or tokens are insecure. | Appropriate factors, secure sessions and revocation |
| A08 Software or Data Integrity Failures | Untrusted changes are accepted. | Integrity checks and controlled update paths |
| A09 Logging and Alerting Failures | Incidents remain undetected or cannot be reconstructed. | Purposeful, data-minimising event logs |
| A10 Mishandling of Exceptional Conditions | Exceptional states cause unexpected, insecure behaviour. | Defined error paths and secure default responses |

**SQL injection** arises, for example, when uncontrolled characters from a form are interpreted as part of an SQL command. **Parameterised queries** separate data values from commands. **Cross-Site Scripting (XSS)** concerns content processed as active code in the wrong browser context; context-appropriate output encoding is central here. **Server-Side Request Forgery (SSRF)** describes the misuse of server-side access to unwanted destinations; network segmentation alone cannot eliminate this flaw completely.

OWASP changed its categories in 2025 compared with 2021: for example, A03 now covers software supply chain failures, while misconfigurations are under A02. Anyone comparing an older list with a newer one must therefore pay attention to **the year and category names**, otherwise different issues are incorrectly equated.

## Operational security: Patching, monitoring and recovery {#S9}

A secure architectural diagram does not guarantee a secure service after a year of operation. Software receives updates, certificates expire, devices are replaced, permissions remain after role changes and external dependencies change. Security is therefore an **operational process**.

### The lifecycle model

The **NIST Cybersecurity Framework 2.0** describes six interconnected functions: **Govern**, **Identify**, **Protect**, **Detect**, **Respond** and **Recover**. These phases are not simply a staircase to be climbed once; many activities run continuously in parallel.

``` text
Govern / Responsibilities and objectives
            |
Identify -> Protect -> Detect -> Respond -> Recover
    ^                                 |         |
    +-------- Lessons learned <-------+---------+
```

**NIST SP 800-61 Revision 3** of April 2025 explicitly places incident handling within this risk management framework. It replaces the older Revision 2. **Incident response** means knowing responsibilities, appropriately recording an incident, limiting damage, addressing causes, recovering service and feeding lessons back into operations. In addition to technology, this encompasses organisational decisions and potentially legal obligations.

### What a small service actually needs

- **Inventory:** Which servers, accounts, software versions, domains, databases and service providers exist in the first place?
- **Planned updates:** Track security-relevant updates and deploy them with a suitable fallback option; do not blindly put every version into production without testing.
- **Key and account maintenance:** Disable unnecessary accounts, keep secrets out of source code, minimise access permissions and review them after changes.
- **Limited logging:** Trace failed logins, unusual permission-related access and failures; do not write passwords, session tokens or unnecessary personal content to logs.
- **Recovery:** Create backups **and** verify recovery regularly. A backup that has never been restored is not yet a proven recovery strategy.
- **Operational limits:** Rate limits, capacity planning, alert thresholds and budget controls can limit abuse and unintended costs.

The mere existence of a firewall does not fully address any of these topics. Conversely, a single small hobby program does not need to imitate a full-time security team. What matters is a small number of measures that can genuinely be operated and understood in the particular context.

## Virtual private networks, zero trust and remote access {#S10}

A **VPN** (*Virtual Private Network*) establishes a logically protected communication path over another network. This can be useful if employees or one's own devices are to access internal services. However, a VPN does not prevent an *already authorised and compromised device* from abusing internal services. It replaces neither permission checks nor updated endpoints.

**Zero trust** is not a single product and does not mean “nobody is allowed to do anything”. The fundamental idea is that network position alone does not confer lasting trust. Access is justified according to identity, device state, resource, context and policy, and limited as narrowly as possible. There are gradual transitions: a small private system can implement the most important idea with separate user accounts and the fewest possible privileges without building a complex enterprise platform.

| Model | Strength | Limitation |
| --- | --- | --- |
| Home router/NAT only | Simple default shielding against many incoming contacts | Not a complete protection and permissions architecture |
| Segmentation and firewall | Limits communication paths between areas | Does not protect against every application weakness |
| VPN | Protected remote access to selected networks | Scope of trust may be too broad |
| Identity- and resource-based checks | Narrower access to specific services | Requires maintained identities and rules |
| Completely separate infrastructure | Reduces some shared failure and attack paths | More devices, costs and operational effort |

**When is it excessive?** A purely offline media catalogue that exposes no data externally needs no VPN access, public identity provider or internet firewall in front of a non-existent web API. **When is it necessary?** As soon as sensitive data belonging to other people or administrative access becomes publicly accessible, protection requirements and the consequences of an error increase considerably.

## Three continuous application architectures {#S11}

### Example A – The local media catalogue

A program runs only on a personal computer and manages local video and image metadata. The main danger here may be a faulty update or loss of the hard drive, rather than a targeted attack on a public API.

``` text
Local computer
  |-- User interface
  |-- Local application
  |-- SQLite / files
  \-- Separate backup copy

No publicly accessible web service required
```

**Useful:** Keep the operating system up to date, use standard user privileges, test backups and consciously select downloaded programs and dependencies. **Not automatically useful:** one's own cloud server, external user management, microservices and complex network traffic. If synchronisation is introduced later, new trust boundaries arise – the model must then be reassessed.

### Example B – A public web application with a database

A website provides private users with an analysis function. The frontend may be public, but the database must not be directly accessible from the internet. The web service checks login and the record's relationship to the user.

``` text
Browser / internet
       |
      HTTPS
       |
       v
Public web service / reverse proxy
       |
       v
API: Authentication + object authorisation + limits
       |
       | Defined internal connection only
       v
Private database
       |
       v
Tested backups / recovery
```

**Typical errors:** The database is accidentally given public network access, a new API route omits the object check, a backup is placed in the web directory or logs contain confidential tokens. **Pragmatic countermeasures:** Only necessary connections, server-side authorisation, secure software configuration, an update path, access logs and tested recovery.

Cost is part of the question: a second instance, an external firewall service or a continuous security scanner costs money and maintenance effort. These are not automatically the most sensible first investment; systematic permission checks and a working backup can provide greater immediate benefit.

### Example C – A connected sensor with cloud integration

A microcontroller sends measurements to a central service. The device may be used for years and may have limited memory and processing power. The loss of a single device key or a faulty update can already affect numerous devices.

``` text
Sensor -> Microcontroller -> Secured transmission path
                                  |
                                  v
                          Device ingress / API
                                  |
                           Separate device identities
                                  |
                                  v
                             Storage / analysis
```

**Security objectives:** Measurements should not be arbitrarily manipulable, an individual device must not automatically be able to administer other devices, and necessary updates must be deployable in a controlled manner. **Limitations:** Encryption requires energy and computing time; certificate and key rotation must work despite intermittent connectivity. If the sensor merely controls a local lamp, a mandatory cloud connection would instead be an additional source of failure without a compelling benefit.

## Two small calculations: Size is not the same as security {#S12}

### A /27 subnet

For IPv4 with 32 bits and `/27`, 5 bits are not reserved for the network prefix: $32 - 27 = 5$. The result is $2^5 = 32$ addresses in the block. In the classical subnet with network and broadcast addresses, 30 host addresses remain. The calculation explains **address capacity**, not how many of these addresses can actually be operated securely. It also says nothing about which connections the firewall permits.

### Why bandwidth and latency are different

**Hypothetical:** A 100 MB file contains approximately 800 megabits in a simplified calculation. At an ideal 100 Mbit/s, transmission alone takes at least $\frac{800}{100}=8\,\text{seconds}$. Protocol overhead, competing use, server load and packet losses increase the actual time. A 10 ms latency to a server does not make bandwidth arbitrarily large; a 1 Gbit/s connection does not automatically make a slow database query fast.

Security also affects the architecture: additional checks create work, but omitting fundamental access controls is not a permissible optimisation. One should measure *which* check incurs costs before reducing the protection architecture.

## Decision framework and limitations {#S13}

Five short questions help before implementing a technical measure: **What problem is being solved? Who is at risk? What is the simplest effective protection? Who maintains it? How will its failure be detected?**

| Situation | Often useful | Often unnecessary or insufficient |
| --- | --- | --- |
| Single offline PC | Updates, permissions, backup, trustworthy software | Public API and enterprise zero trust platform |
| Home network with guest devices | Separation, router maintenance, separate access | Blind trust based on the same Wi-Fi SSID |
| Small public web service | HTTPS, server permissions, patch maintenance, logs, restore test | Merely “port 443 is open, so everything is secure” |
| Cloud with sensitive data | Protection requirements, minimised IAM permissions, separate resources | Unquestioned trust in the cloud provider |
| Long-lived IoT device | Device identities, update path, protection against key loss | Mandatory internet connectivity for every function |

The most important relationship is this: **Networks transport data. Security determines the conditions under which that transport and subsequent processing are permitted.** Secure communication, secure applications, secure data storage and secure operation are different tasks that must fit together.

| Term | Brief description |
| --- | --- |
| IP | Addressing and forwarding between networks |
| TCP / UDP / QUIC | Different transport mechanisms for application data |
| DNS | Name resolution; not a substitute for website authentication |
| Port | Technical endpoint of network communication |
| CIDR | Description of network prefixes, e.g. `/27` |
| VLAN | Logical local network segment |
| Firewall | Rule-based control of communication flows |
| TLS | Protection of data transmission and peer verification |
