# Database architecture decisions – cross-cutting guide M3-L1–M3-L6

**Purpose:** Supplementary reading for the completed core area C. It brings the existing lessons together into a systematic approach to decision-making that readers can follow. It is **not an additional compulsory lesson** or a Master’s elective module. There are no exercises, installations or instructions to set up a service.

## 1. Make decisions based on problems, not products {#S1}

The terms *replication*, *partitioning*, *sharding*, *Serializable* and *Point-in-Time Recovery* describe **different requirements**. They are not interchangeable stages in an inevitable journey towards the cloud.

Anyone running a small database must first answer the question: *What is not yet working reliably or quickly enough?* A complicated answer to the wrong problem increases operating costs without resolving the actual shortcoming.

| Observed problem | What to examine first | Possible technical response | New costs or limitations |
| --- | --- | --- | --- |
| Queries become slow | Query plan, missing indexes, data volume, I/O | Index, different query, cache; read replica if appropriate | Additional storage and maintenance; the replica may lag behind |
| A server failure interrupts the service | Desired recovery time, type of failure | Standby, failover, switchover and fencing strategy | Additional system, monitoring, role conflicts |
| Acknowledged data must not disappear | Transaction and failure model, commit rule | Stronger commit acknowledgement plus controlled failover | Higher write latency, lower write availability |
| The write workload no longer fits on one node | Hotspots, data model, demonstrated bottleneck | Distribution by shard key if appropriate | Routing, cross-shard transactions, rebalancing |
| Concurrent operations violate business rules | Integrity conditions, isolation, race conditions | Atomic updates, constraints, appropriate isolation | Transaction aborts due to conflicts, waiting times, domain complexity |
| Data is deleted, damaged or encrypted | Which last *clean* state is available? | Independent backup, versioned backup, PITR | Storage, key management, recovery effort |

**First rule of thumb:** Do not start with the supposedly largest system and work backwards to simplify it. When requirements are simple, a single, properly maintained database is often the technically better choice.

## 2. Four protective functions, four different promises {#S2}

With a database, it is important to distinguish **which question** is to be answered:

1.  **Transaction:** Is a group of related changes completed in a logically correct manner? For example, making a reservation and reducing the stock count take effect together.
2.  **Replication and high availability:** Is there another node that can take over if a failure occurs, and is the switchover process protected?
3.  **Sharding:** Can a large data set or a distributable workload be divided among independently responsible data partitions?
4.  **Backup and recovery:** Can an earlier, independent and ideally error-free state be restored?

The second does not replace the fourth. An accidental deletion can propagate to every replica within seconds. Likewise, sharding does not automatically make an application faster: a query across *all* shards may even become more costly. And a database with ACID transactions remains unprotected against certain kinds of damage without an independent backup.

``` text
                       Application
                            |
                       Transactions   <- business correctness
                            |
                    Database / primary system
                         /       \
             Replication       Distribution  <- availability / load
                         \       /
                         Data set
                            |
                   independent backups  <- recovery
```

The sketch does not mean that every layer is actually needed or must be implemented in precisely this arrangement. A small system can meet several of these requirements with a single process and separate backups.

## 3. Three development paths that can be followed {#S3}

### Path A – Personal media catalogue

A local programme manages 150,000 videos and image files with tags and notes. The number of entries alone does not require a distributed database. **SQLite with appropriate indexing** can handle the work very well. The main risk of loss concerns the notes and associations entered by the user. A consistent, independently stored backup is therefore more valuable than a supposedly state-of-the-art multi-node architecture.

For example, someone copies only the main file of a running SQLite database while additional journal or WAL files are in use. This may not capture the desired complete state. SQLite provides an **Online Backup API** and `VACUUM INTO` for this purpose; a backup should also be opened as a test. The media files themselves are a separate backup concern.

### Path B – Small public online service

A web application manages customers, reports and analysis jobs. A single PostgreSQL instance is initially sufficient. If searches become slow, the investigation starts with queries, indexes, caching and measuring bottlenecks. Only when a very large number of **read** requests becomes a limiting factor for the server might a read replica help. However, it may not return the very latest record.

If the application becomes business-critical, a standby can reduce downtime after a hardware failure. However, the **failover rule** must define which node is allowed to write. The mere existence of a synchronous copy is not yet a complete backup or switchover strategy. Independent backups and recovery tests remain necessary.

### Path C – Very large service with a highly distributable write workload {#pfad-c-sehr-grosser-dienst-mit-stark-verteilbarer-schreiblast}

A shard key becomes worth considering only when measurements demonstrate that reasonable local optimisation or the capacity of a single database node is no longer sufficient. For example, data belonging to different customers can reside on separate shards. Ideally, most of a customer’s business operations remain within the same data partition.

A balance transfer **between** two customers on different shards becomes problematic: a successful debit on shard A does not make the credit on shard B atomic. Distributed transactions or multi-stage processes appropriate to the business domain must then be justified separately. `Sharding` alone says nothing about the transaction consistency actually guaranteed.

**Additional limitation:** Hash-based distribution often distributes sequential identifiers more evenly, but scatters range queries across shards. A particularly active customer can remain a workload hotspot even with a good hash key.

## 4. Do not confuse three failure scenarios {#S4}

### A. The acknowledgement is lost – was the order created? {#a-bestätigung-ist-verloren-wurde-die-bestellung-angelegt}

The browser sends a request. The database acknowledges success, but the response does not reach the browser. Resending the request may generate a duplicate booking. An **idempotency identifier** makes it possible to recognise the same intended operation again. This is a problem of application semantics, not of the number of database nodes.

### B. The primary server fails – what data may the replica acknowledge? {#b-der-primärserver-fällt-aus-welche-daten-darf-das-replikat-bestätigen}

With asynchronous replication, the most recently acknowledged changes may be missing from the standby. With synchronous replication, the guarantee depends on **which standby acknowledges what** and whether the correct node is promoted to the new primary server. The old primary must not subsequently resume writing undetected: split-brain must be prevented. A standby without a protected mechanism for assigning roles is not a complete high-availability solution.

### C. An erroneous deletion has been replicated everywhere – which copy can still help? {#c-eine-fehlerhafte-löschung-wurde-überall-repliziert-welche-kopie-hilft-noch}

Once the error has reached every replica, rapid replication is of no help. What matters now is the most recent backup state **that can be restored from before the error**. With a suitable physical backup and an uninterrupted sequence of archived WAL records, PostgreSQL can provide **Point-in-Time Recovery**. An ordinary `pg_dump`, however, is not a base for WAL replay. Other components, such as object stores, keys and file references, must also be consistent with the reconstructed state.

## 5. Two numerical examples: a target is not the same as a guarantee {#S5}

**Target A:** A service defines an RPO of five minutes. A single daily backup at 02:00 will normally not meet this target if a failure occurs at 17:00. The interval in this constructed example is **15 hours**. The problem may remain unresolved even with an additional server, for example if all copies incorporate the same operational error.

**Target B:** A service defines an RTO of 30 minutes. The available backup contains all important data, but restoring it, configuring the system and checking the application takes two hours. The RPO may have been met, but **the RTO has not**. Measurable recovery tests provide more meaningful insights here than an untested operational promise.

These values are **constructed teaching examples**, not benchmark results or general industry targets.

## 6. Bridge to advanced Master’s studies {#S6}

Core area C provides the technology. The completed Master’s core lessons show how to make well-founded statements about it:

- **[M7-L2 – Correctness and computability](M7-L2.md):** A business invariant such as ‘no double sale’ must be defined explicitly. Whether a method preserves it is a question of correctness.
- **[M7-L3 – Distributed systems](M7-L3.md):** Failures, network partitions, consensus and the absence of a global clock explain why a successful local state does not prove a global guarantee.
- **[M7-L4 – Security and architectural decisions](M7-L4.md):** Protection requirements, risk, permissions and operational effort constrain the appropriate architecture.
- **[M7-L6 – Research methods and synthesis](M7-L6.md):** An architectural decision is convincing only when criteria, assumptions, counterexamples and limitations of measurement are documented.

**Summary:** Databases do not become better simply by having as many distributed functions as possible. The appropriate architecture meets verifiable requirements with as little unnecessary coordination and operational effort as possible.
