# Three continuous scenarios

These examples are **purely explanatory**. Neither accounts nor running servers are required.

## Example 1: Small online tool {#S1}

A person operates a simple paid website with user accounts, a web application, an interface and a relational database. Initially, the basic design should be able to run on a single host with adequate capacity.

``` text
User → Web interface → Application process → Database
```

Points to explain: security, accounts, backups, updates, payment, support and ongoing costs.

## Example 2: The same service with higher demand {#S2}

The service is heavily used. First measure bottlenecks, then compare possible measures: caching, multiple service instances, queues, read replicas — and sharding only if it is actually necessary.

``` text
                       ┌→ Instance A ─┐
User → Load balancer                  ├→ Data storage
                       └→ Instance B ─┘
```

Points to explain: costs and new sources of failure, shared state, consistency and failure scenarios.

## Example 3: AI jobs and, later, devices {#S3}

Jobs enter a queue through an interface; specialised workers process them, store the results and report their status.

``` text
User → API → Queue → AI worker → Results storage
               │
               └→ Status / error handling
```

Points to explain: duplicate processing, retries, GPU costs, privacy protection, failure handling and — for devices — local control rather than exclusive dependence on the internet.
