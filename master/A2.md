# Hosting, scaling and cloud operations – decision-making guide

**Purpose:** Cross-cutting reading material for M2-L1–M2-L5 and M4-L1–M4-L5. It supplements existing lessons and **counts neither as a compulsory lesson nor as a Bachelor’s or Master’s elective lesson**. The examples are hypothetical; no installations or exercises are required. Every architecture decision starts with the problem to be solved, not with the choice of a cloud brand.

## 1. Five decisions that must not be confused {#S1}

| Decision | Examples | Primarily addresses | Does not automatically address |
| --- | --- | --- | --- |
| Where does execution take place? | Own computer, shared hosting, VPS, PaaS | Deployment and division of responsibilities | Data protection, security, financial viability |
| How is the system divided? | Monolith, separate services, workers | Responsibilities and processing paths | Data consistency, resilience |
| How is load handled? | Faster host, cache, multiple instances, queue | A particular throughput or latency bottleneck | Defective business logic, dependence on a central database |
| How is a disruption handled? | Health checks, replicas, restart, backups | Specific failures and recovery | Every conceivable fault, loss of data already processed inconsistently |
| How are risks kept manageable? | Permissions, quotas, budgets, checks | Limiting abuse, cost and compliance risks | Preventing every charge or meeting all legal requirements |

**Principle:** High availability is not the same as scaling. A second web instance can compensate for the failure of the first, while the shared database remains a single point of failure. Conversely, a powerful single server can handle a great deal of load without being redundant against hardware failure.

## 2. Three realistic stages of development {#S2}

### Stage A: Documentation website and small tool

``` text
Browser → HTTPS/web hosting → static files or simple PHP application
                              └→ small database, if needed
```

**Suitable when:** there are few users, simple states, modest recovery requirements and a manageable budget. A conventional web host or VPS may be sufficient. **Do not add prematurely:** separate Kubernetes clusters, message brokers, microservices or multiple regions. These increase setup and operational responsibilities without automatically providing a measurable benefit.

**Remaining responsibilities:** domain, updates, data access, backups, permissions and any personal data – regardless of whether the provider operates parts of the infrastructure.

### Stage B: Online analysis tool with occasional load peaks

``` text
Browser → web application/API
          ├──▶ persistent job database
          └──▶ bounded queue → worker
                               ├──▶ result storage
                               └──▶ status back to web application
```

The interactive response initially confirms the **acceptance** of a job, not necessarily its successful completion. A queue decouples acceptance from computationally intensive processing. However, it cannot absorb unlimited load: over the long term, the average processing rate must at least keep pace with average demand; otherwise waiting times increase.

**Constructed numerical example:** Three workers each take an idealised 30 seconds to complete a job. One worker completes 2 jobs/minute and three workers complete 6. If 12 jobs/minute arrive, the backlog grows by an average of 6 jobs/minute; after 10 minutes, approximately 60 additional jobs are waiting. Three additional workers of the same speed would be needed simply to match the average arrival rate mathematically – without any provision for spare capacity, failures, database limits or startup times. In practice, a safety margin would be necessary.

**Duplicate delivery:** If an acknowledgement is not transmitted because a connection fails, a job that has already been processed may arrive again. A unique job identifier, together with atomic storage of the completion or billing state, prevents certain duplicate side effects. A mere `if not exists: insert` without protection against concurrent transactions is insufficient. The job itself may still consume computing time more than once.

### Stage C: Service with recurring load and higher availability requirements

``` text
Browser → resilient entry point/load balancer → multiple web instances
                                                ├──▶ shared state/database
                                                └──▶ queue/worker pool
                                                     └──▶ storage / third-party API
```

Multiple availability zones, independent instances, defined recovery objectives and automated rollouts may now be appropriate. The prerequisite is a specifically documented need: which failures should be tolerated? Which data may be lost? What cost increase would be acceptable? What happens if the shared database, an external service or the load balancer fails?

Increasing the number of pods using the Kubernetes Horizontal Pod Autoscaler does not mean that nodes are available. With HPA CPU targets, it is also necessary to clarify whether the metric is measured relative to container CPU requests; not every ‘70% CPU’ refers to the same thing.

## 3. Latency and throughput: two independent objectives {#S3}

**Throughput** describes, for example, jobs completed per minute. **Latency** denotes the time taken by an individual request or job. More concurrent workers may increase throughput while latency per job remains unchanged or even increases because of competing accesses. A fast cache reduces latency for frequently requested content but does not resolve an expensive write transaction. A load balancer does not eliminate a bottleneck in a shared database.

Evaluating a service therefore requires at least three measurement perspectives: accepted demand, work completed successfully and waiting/response time. Utilisation alone does not reveal whether users receive the service. For an AI service, for example, **time until processing begins**, **time to the first result** and **total processing time** are distinct metrics.

## 4. Think about fault protection in layers {#S4}

| Incident | Useful protective measure | Limitation |
| --- | --- | --- |
| A web instance hangs | Liveness check and restart, redundant instance if appropriate | Errors in application behaviour are possible despite a ‘green’ health check |
| Service does not accept requests | Readiness check, remove it from the target group | Only works with healthy alternative instances |
| Worker dies after the response has been saved | Redelivery, idempotent completion | Duplicate charges are possible without atomic state changes |
| Rollout contains a software bug | Canary deployment/rollback and monitoring | Database changes are not automatically reverted |
| Central database fails | Restore and, where appropriate, carefully managed failover | Replication is not a substitute for a backup; only suitable commit/failover rules protect acknowledged data |
| Unauthorised parties generate expensive API jobs | Authorisation, limits, budget alerts, job quotas | Alert-only budgets do not stop all charges |

A **Recovery Point Objective (RPO)** is a defined maximum tolerable period of data loss, and a **Recovery Time Objective (RTO)** is a target time for resuming operations. They describe objectives, not already proven properties. Evidence is obtained only through appropriate tests and measured recovery under specific failure assumptions. Related topics: [M3-L2](M3-L2.md), [M3-L6](M3-L6.md) and [M7-L4](M7-L4.md).

## 5. Reading a Service Level Objective correctly {#S5}

Suppose a service selects a success rate of 99.5% for **successful requests** in an explicitly defined month. With exactly 100,000 requests included, the calculated error budget is $100\,000\times(1-0{,}995)=500$ failed requests. This is a **request-based** metric.

A **time-based** monthly availability of 99.5% would be something different: a constructed 30-day month contains $30\times24\times60=43\,200$ minutes; of these, $0{,}005\times43\,200=216$ minutes are calculated as unavailable. It would be wrong to equate the two values without an explicit measurement definition. Which HTTP status codes, timeouts and regions count as failures must be defined.

An **SLI** defines the metric, an **SLO** its target; an **SLA**, by contrast, is an agreement with possible consequences. When operating a small private service, an internal SLO can be useful without promising a contractual guarantee that can scarcely be sustained.

## 6. Limiting costs is a multi-layered architecture decision {#S6}

A budget alert is fundamentally a notification, not a switch that turns spending off. Cloud expenditure arises from running instances, storage, network traffic, separate services, API consumption and retry loops, among other things. Minimising technical expenditure must be incorporated into the architecture before publication.

**Example of the scope of a particular provider’s solution (as of 5 November 2026):** Google Cloud documents spend cap budgets for certain services within a project. When such a budget reaches its threshold, **new usage of that particular selected service** may be paused. Other services, fixed costs for persistent resources and requests already in progress may continue to incur costs; enforcement is not necessarily immediate. This is not a universal spending cap for the entire project.

Practical protection combines access permissions, user quotas, limited file sizes, maximum job run times, upper limits on retries and workers, early warnings and regular invoice checks. The financial comparison also takes support, backups, refunds and one’s own operational time into account. See [M4-L3](M4-L3.md) and [M4-L4](M4-L4.md).

## 7. Decision matrix: the most complex option does not win {#S7}

| Requirement | Single web host/VPS | Managed platform + DB | Cluster with multiple services |
| --- | --- | --- | --- |
| Simple static website | Usually sufficient | Also possible, often unnecessary | Usually oversized |
| Small PHP application with moderate load | Often well suited | Suitable depending on features | Usually unnecessary |
| More users without operating one’s own server | Requires operational skills | Often less operational effort | High architecture and monitoring effort |
| Irregular computationally intensive jobs | Possible, but consider shared resources | Queue/worker may be suitable | Possible where demand is greater |
| Demanding resilience and scaling requirements | Limitations of a single node | Depends on the provider’s specific offering | Possible with a targeted design, but by no means automatically correct |
| Lowest possible maintenance effort | Low with simple hosting, higher with a VPS | Often less infrastructure maintenance | Usually more extensive |

The entries are **qualitative heuristics, not a general recommendation of any provider**. The architecture that is actually sustainable depends on data volume, load profile, budget, legal requirements, team knowledge and tolerance of failures.
